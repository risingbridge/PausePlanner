# Thorough (Experimental)

**Thorough (Experimental)** is a fork of [Thorough](Algorithm-Thorough.md) (`src/scheduler/algorithms/thorough/`, copied wholesale into `src/scheduler/algorithms/thorough-experimental/`), kept as a **standing incubator for experimental features** rather than a permanent fifth mode. It is not meant to stay a fixed, documented algorithm the way Quick, Balanced, Thorough, and Refine are — it's where a new idea gets tried against a real, working branch-and-bound search before (if ever) graduating somewhere more permanent, or being discarded. Today it carries exactly one such experiment: **required position assignments**. Expect this document, and the fork's contents, to keep changing as new experiments land here.

Because it's a genuine fork rather than a shared abstraction, **Thorough and Thorough (Experimental) now diverge permanently.** A fix or improvement made to one does not automatically apply to the other. That's an accepted cost of using a fork as an incubator, not an oversight — see the root `CLAUDE.md` and the task that introduced this fork for the reasoning.

## What's identical to Thorough

Everything: inputs, output shape, hard rules, the free per-slot lower bound, the two-phase lexicographic search, symmetry breaking, dead-end pruning, the Quick/Balanced warm start, and the Web Worker wrapper (its own separate worker instance/module — never shares one with Thorough's). Before required-position support was added, the fork's output was verified byte-identical to Thorough's on a real multi-staff scenario, proving the copy itself introduced no drift.

## What's different: required positions

A `PositionRequirement` (`{ id, positionId, start, end }`) is a **positive** constraint on a `Staff` member — "work this position for this window" — as opposed to a `TimeBlock`'s negative one ("unavailable for this window"). Requirements are entered on the Staffing page and validated there (window inside the shift, no overlap with blocks or other requirements, duration within `maxTimeInPosition`, the position open throughout) regardless of which algorithm is selected, but **only Thorough (Experimental) actually enforces them** — Quick, Balanced, Thorough, and Refine treat `staff.requirements` as inert data, exactly as specified for this task; the Schedule page shows a warning banner whenever requirements exist and a non-enforcing algorithm is selected.

### Branching collapses to one choice, same as protection already does

At any slot inside an active requirement window, a person's branching collapses to exactly one legal action — work the required position — the same structural trick `minPositionLength` protection already uses in Thorough (see [Algorithm-Thorough.md](Algorithm-Thorough.md)'s "Branching" section): required people never enter the free/joint-enumeration machinery at all. They're resolved in their own pass, once every requirement claim for the slot is known.

That resolution reuses existing machinery rather than adding new eviction logic: a position claimed by a requirement is removed from the "open positions" set as seen by everyone *else* this slot — exactly as if it had genuinely closed. Anyone else who happened to be holding it (even mid-`minPositionLength` protection) is forced off through the *same* `forcedOff` path a real closure already triggers, with no special-casing needed.

### The one hard failure mode: an unavoidable same-slot bounce

If a person is mid-stint in a *different* position going into a slot their requirement claims, forcing them into the required position would be a same-slot bounce — position A to position B with no rest in between, which is exactly the hard rule the no-bounce constraint exists to forbid. This is checked explicitly: when it would occur, the whole slot's outcome set is empty, making that branch a dead end the search backtracks out of. Entry-time validation can't catch this in general, because whether it happens depends on what the search *chose* to do in the slot immediately before — data entry validation doesn't (and structurally can't) know that in advance.

### continuousMinutes resets at the requirement's start

A requirement is treated as a fresh assignment: `continuousMinutes` resets to one slot's worth of time at the requirement's own start slot, rather than stacking on whatever the person was doing immediately before it. This is what makes the entry-time "duration ≤ maxTimeInPosition" check (validated once, statically, when the requirement is entered) stay meaningful without the validator needing to know the full schedule state in advance — the requirement's own duration is always what's checked against the cap, regardless of what surrounds it.

**A real, tested, and intentional consequence:** if a requirement happens to be immediately adjacent to pre-existing same-position work (no gap), the *visible* output can show a single continuous-looking run longer than `maxTimeInPosition`, even though the algorithm never internally violates the cap in either the pre-requirement stint or the requirement itself — each is independently capped, but the reset means the two aren't merged for accounting purposes. Verified directly: a person naturally working position P was deliberately forced to accumulate exactly `maxTimeInPosition` minutes right up to a requirement's start for that same position P; the requirement (independently within the cap) then ran to completion, and — confirming the reset actually took effect, rather than merely not crashing — she was correctly granted exactly one more slot afterward (bringing her *fresh* count to precisely `maxTimeInPosition`) before being forced off, rather than zero (which is what stacking would have produced).

### The break guarantee vs. requirements: infeasibility is a real, surfaced outcome

If a person's requirements structurally consume every slot where their one guaranteed break could ever start, the **existing** dead-end pruning already catches it correctly with zero additional code: break-domain candidates that fall inside a requirement window are never reachable (required slots never enter the free/break-consideration branch at all), so once the search passes the last domain candidate without that person ever having had the *opportunity* to take a break, the existing "ran out of window without a break" dead-end check fires — pruning every branch, and if it's truly unavoidable, the entire day.

Because Quick and Balanced don't know about requirements, "the warm start already matches the lower bound" can no longer be trusted as proof the warm start is even a *valid* answer once requirements exist — it only speaks to raw coverage, not whether anyone is actually standing in a required position. So whenever any requirement exists, the fast path is skipped unconditionally and the search always seeds its incumbent from `Infinity` rather than the warm start's cost, so any complete, requirement-honoring schedule it finds counts as an improvement. If the search *never* finds one — genuine infeasibility — `runThoroughExperimental` throws a descriptive `Error` (rather than silently falling back to a requirement-ignorant Quick/Balanced schedule) — surfaced through the exact same async/error-handling path the Schedule page's "Generating…" flow already had, extended to show the thrown message instead of a generic one. This was a deliberate choice over inventing a new UI concept or changing `ScheduleResult`'s shape: verified directly with a requirement spanning almost an entire short shift, leaving no room anywhere for the mandatory break — the generator throws instead of ever returning a schedule that silently drops someone's break.

## Everything else

Unchanged from Thorough: the objective, the lexicographic phases, the honest costs (runtime, code weight, explainability), and the relationship to Quick/Balanced as warm starts. See [Algorithm-Thorough.md](Algorithm-Thorough.md) for all of that — this document only covers the delta.
